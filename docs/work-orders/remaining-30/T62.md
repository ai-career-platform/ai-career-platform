## 7. 상세 설계 기준 — 독립 Python Batch Worker (2026-11-06 PM 방향)

**확정 구조:** 크롤러는 FastAPI 요청 처리 스레드/프로세스 안에서 장시간 실행하지 않습니다. 공통 Python 수집 모듈을 독립 CLI **Batch Worker**로 실행하고 Backend는 조회·관리 API를 담당합니다. 상주 크롤러 데몬이나 Celery/Redis는 초기 필수 구성요소가 아닙니다.

### 7.1 책임과 인터페이스
- Adapter: 승인된 출처별 API/CSV/승인된 웹 방식의 `fetch` 인터페이스. 출처별 모듈을 분리하여 외부 형식 변경 시 해당 Adapter만 수정.
- Normalizer: 원천 제목, 기업, 직무, 상태, `source_id`, `external_id`, 게시/마감 시각과 타임존을 표준 입력 DTO로 매핑. 품질 게이트는 T63과 공유하는 명시적 계약으로 전달.
- Worker CLI: `--source-id`와 `--run-id`를 받는 실행 진입점 제안. 호출 방식은 T64와 합의 후 고정; 수집 로그는 `run_id`를 포함하는 구조화된 이벤트로 출력.
- 실행 가능 여부: T61의 APPROVED·enabled·rate limit를 실행 직전에 재확인. 실제 외부 데이터 수집은 T61 승인 전에는 Mock fixture만 사용.
- DB: 최소 권한 앱/수집 쓰기 역할을 사용. SUPERUSER, 웹 관리자 토큰, Staging DB 자격증명을 코드/테스트에 포함하지 않음.
- 외부 네트워크 요청: timeout, 유한 재시도, 지수 백오프(상한 포함), 사이트별 속도 제한, 정상 종료 코드/실패 코드 표준화.
- 원본 응답/파싱 결과 저장은 라이선스와 개인정보 정책에 따르며 T63에서 검증한 데이터만 승인된 경로로 저장.

### 7.2 경계와 예시 디렉터리 (설계 제안; 실제 구현 위치는 개발 PR에서 확정)
```text
crawler/
  adapters/{base.py,approved_source_a.py}
  schemas/{raw.py,normalized.py}
  normalizers/
  jobs/run_crawler.py
  tests/{fixtures/,test_adapters.py,test_worker.py}
```
`services/ingestion.py` 등은 실제 정식 Backend 패키지 구조를 고려하여 PR에서 결정. 웹 API에 `subprocess`로 장기 실행을 매달아 요청 완료까지 기다리는 패턴 금지.

### 7.3 테스트/검증 시나리오
1. 승인 Fixture → DTO 매핑(원본 식별자/타임존 포함)과 건수 일치.
2. 필수 필드 없음, 잘못된 날짜, 예상치 못한 응답 구조 → 검증 실패/격리 로그.
3. HTTP 429/5xx, 연결 끊김, 타임아웃 → bounded retry, rate limit 및 run 결과 기록.
4. 출처 HOLD/DENIED 또는 disabled → 외부 요청 0건.
5. 동일 fixture 반복 실행 → T63 멱등성 계약 충족, 저장 중복 0.
6. Adapter A 오류가 다른 출처 B의 계약/테스트를 깨지 않는지 회귀 확인.
