## 7. 상세 설계 기준 — 품질·멱등성 게이트 (2026-11-06 PM 방향)

**책임:** T62가 수집·정규화한 입력을 저장하기 전에 품질 검증하고, T64의 재실행·실패 복구가 데이터를 중복 생성하지 않도록 합니다. 실제 DB 제약·컬럼 변경은 T09 Migration 승인 범위에서만 적용합니다.

### 7.1 필수 검증 규칙
- 식별: `(source_id, external_id)`가 안정적일 때 동일 출처·외부 ID를 대표 키로 사용. 외부 ID가 없는 출처는 승인된 대체 키 전략을 별도로 문서화하며 기업명/제목 단독 자동 병합 금지.
- 표준화: 제목·회사·직무 코드, 필수 텍스트 공백, URL, 게시·마감 시각, 타임존 UTC 저장/KST 표시 규칙 검증.
- 시간: 만료 공고, 재게시, 삭제·비활성 공고를 구분. `expired`/삭제 플래그의 처리 정책과 원천 증빙 기록.
- 변경: 동일 ID로 제목/마감일이 바뀐 경우 업데이트 정책, 최신성, 원본 추적 정보 및 변경 횟수 정의.
- 개인정보·보안: 비승인 필드·토큰·세션 쿠키·PII 로그/Raw 저장 제한; 정책 위반은 저장 차단.
- 출처별 품질 지표: fetched/normalized/inserted/updated/duplicate/skipped/invalid/failed 건수, 오류 코드·사유 코드.

### 7.2 원자성·재처리
1. 유효한 공고는 안정 식별자 기반 Upsert 또는 동등한 멱등 처리(상세 SQL은 승인 계약에 맞춰 확정).
2. 실패 항목은 다른 유효한 공고의 적재까지 무조건 중단하지 않되, 치명적인 계약 오류에는 run 수준 FAIL을 남김.
3. 수집 중 중단 후 동일 `run_id` 또는 재실행 시 추가 중복 없음. 데이터 저장과 진행 체크포인트의 일관성 검증.
4. 출처 삭제/수정 정책은 T61 라이선스·보존 정책 및 T05/T09 데이터 계약과 일치해야 함.

### 7.3 QA Fixture/재현
- 정상 공고, 같은 외부 ID 중복 2회, ID 없는 공고, 필수값 누락, 타임존 경계, 마감 공고, 수정·재게시, 수집 실패 후 재시도.
- 최소 두 번 연속 동일 fixture 처리 시 `신규 중복 0`, 재시도 실패 후 정상 복원, 집계 개수의 보존 법칙 검증.
- SQL 제약/인덱스 테스트는 **개발자 로컬 격리 PostgreSQL**에서 수행. Staging DML/DDL 금지.
- 오류 리포트는 `run_id`, `source_id`, `error_code`, 비민감 증거만 포함.
