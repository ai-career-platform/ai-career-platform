## 7. 상세 설계 기준 — Scheduler / 관리자 API / 운영 (2026-11-06 PM 방향)

**아키텍처 결정:** **독립 Python Batch Worker(T62) + PostgreSQL 스케줄·실행 이력 + FastAPI 관리자 API + Ubuntu systemd timer**를 기본 구조로 채택. 하루 새벽 1회 실행하므로 24시간 상주하는 크롤러 데몬은 사용하지 않음. Celery/Redis는 병렬 처리·규모 확장 필요성 확인 후 별도 결정.

### 7.1 프로세스·실행 흐름
```text
관리자 React UI (후행 연계 / T64의 UI 직접 구현 범위 아님)
       ↓ (관리자 인증·RBAC, HTTPS)
FastAPI 관리자 API → PostgreSQL schedule/run/event 설정·조회
                            ↑                ↓
Ubuntu systemd timer (예: 매 5분 dispatcher 기동)
       ↓
Dispatcher: DB의 enabled/next_run_at/승인 출처 검사 → 단일 run claim
       ↓
별도 Python Batch Worker (T62) → 검증(T63) → 승인 DB 적재
       ↓
run_id 단위 진행률·로그·실패 사유·최종 결과 저장 → 관리자 API 조회
```
- `systemd timer`는 **설정된 수집 시각 자체를 하드코딩하지 않고**, 5분 간격으로 DB의 실행 예정 작업을 점검하는 용도. 실제 스케줄은 DB에서 변경.
- 기본 제안: `Asia/Seoul` 매일 **03:00 KST 1회**. 실제 시각은 PM 승인 전에는 예시로만 취급. 변경 시 타임존과 다음 실행 시각을 재계산하고 이력 남김.
- `Persistent=true`로 누락된 dispatcher를 재실행할 수 있지만 서비스가 오래 중단됐을 때 과거 실행을 전부 일괄 수행하지 않도록 **최대 1회 보충 실행 / 유효 시간창**을 별도 정책으로 정의.
- 매 실행마다 DB lease/고유 제약 또는 advisory lock 등으로 **중복 claim 방지**. 수동 실행과 예약 실행 동시 요청 시 충돌을 안전하게 거절/큐잉.
- Batch Worker는 run 단위 프로세스로 분리. timeout, 종료 코드, 강제 중단/재시작, heartbeat·stale run 정리 정책 포함.

### 7.2 관리자 API 계약(초안; T06·T15/관리자 RBAC 계약 확정 후 경로 승인)
| 관리 기능 | 예시 API | 보호 규칙 |
|---|---|---|
| 스케줄 조회/변경 | GET/PATCH `/api/v1/admin/crawler/schedules` | 관리자만 수정, 감사 로그 |
| 소스 활성화/비활성화 | GET/PATCH `/api/v1/admin/crawler/sources` | T61 비승인 출처 활성화 불가 |
| 수동 실행 요청 | POST `/api/v1/admin/crawler/runs` | idempotency key, 실행 중복 거부 |
| 실행 목록/상세 | GET `/api/v1/admin/crawler/runs`, GET `.../{run_id}` | 페이지네이션, 접근통제 |
| 실행 로그 | GET `.../{run_id}/events` | 필터·페이징, Secret/PII 마스킹 |
| 실패 재처리 | POST `.../{run_id}/retry` | 유한 횟수, 권한·중복 검증 |

FastAPI 요청 처리 중 수집 작업을 직접 실행하지 않고 **명령/설정을 저장한 뒤 즉시 202 Accepted 등 상태만 반환**하도록 제안합니다. 관리자 UI 구성·API 라우터 소유는 담당 Backend/Frontend 기존 일감과 연계하며 중복 구현하지 않습니다.

### 7.3 DB 상태 모델(논리 계약; Migration 승인 전 테이블 생성 금지)
- `crawler_schedules` 후보: schedule_id, source_id, enabled, timezone, local_time, next_run_at, last_run_at, updated_by, updated_at.
- `crawler_runs` 후보: run_id, source_id, trigger(scheduled/manual/retry), requested_by, status(PENDING/RUNNING/SUCCEEDED/PARTIAL/FAILED/CANCELLED), started_at, ended_at, heartbeat_at, counters, error_code.
- `crawler_run_events` 후보: event_id, run_id, occurred_at, level, event_type, safe_message, metrics.
- **기존** `data_sources`·`ingestion_runs`·`audit_events`의 정의와 비교해 **우선 재사용**. 별도 후보 테이블 추가가 필요하면 T05/T09 데이터 모델 리뷰 및 Migration 승인 후 진행.

### 7.4 로그·오류 처리 및 관리자 화면
- 관리 화면 표시: 활성화 여부, 실행 주기, 다음/최근 실행, 진행 단계, processed/inserted/updated/duplicates/failed 건수, 오류별 건수 및 세부 기록.
- 로그는 `run_id/source_id/stage/timestamp/level/error_code` 구조화, 민감 데이터 마스킹, 보존·삭제 정책(T61)에 따름.
- 출처별 Adapter 오류가 발생해도 다른 출처 작업을 독립 추적. 반복 오류는 해당 출처만 중단·재검토 가능.
- 오류 수정은 T62 Adapter 변경 → 해당 Fixture pytest → PR/CI → 승인된 배포 → 실패 건 재실행. **관리자 대시보드에서 임의 Python 코드 편집/실행 금지**.
- 관리자 UI는 기존 관리자 Frontend 일감에 후속 연계. T64에서는 API 및 운영용 계약·로컬 검증과 UI 인계 명세까지 필수.

### 7.5 테스트/DoD 구체화
1. **스케줄:** 변경된 KST 실행 시각이 DB 기반 다음 실행에 반영됨. disabled 시 실행 0건.
2. **수동·예약 경쟁:** 동시에 호출해도 동일 출처/대상 run을 두 번 claim하지 않음.
3. **장애:** 429/timeout/worker 강제 종료·재기동, heartbeat timeout, 실패 재시도 상한·복구 확인.
4. **멱등성:** 같은 입력을 두 번 처리해도 신규 중복 0(T63 계약).
5. **권한:** 비관리자 스케줄 변경·수동 실행·재처리는 401/403. 승인되지 않은 출처는 관리자라도 실행 거부.
6. **관측:** run 상태 전이·카운터·오류·로그·실행 시간·누락 실행 정책에 대한 테스트와 대시보드 조회 계약 작성.
7. **증빙:** systemd timer/service unit **초안**, dispatcher/runner, 예시 관리자 API, 격리 테스트 로그·pytest/JUnit/상태 변화 증빙, 운영 runbook·복구 절차 제출.

**운영 활성화 게이트:** T61 승인·T62/T63 테스트·T28 운영 인프라·보안/권한·T09 DB 계약·PM 배포 승인이 모두 충족되기 전에는 Staging timer/Batch를 켜지 않습니다. 관련 테스트는 로컬 격리 시스템에서만 수행합니다.
