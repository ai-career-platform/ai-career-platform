> **담당 역할:** QA/운영 · **우선순위:** P1 · **실제 담당자:** 미배정  
> **선행 일감:** T12,T13,T14,T19,T28,T29 · **기준 브랜치:** `main`

## 1. 목적과 작업 범위
승인된 Frontend·Backend·DB 버전의 Staging 통합 동작과 장애 시 복구 절차를 검증.

## 2. 작업 수행 지시
1. 작업 시작 전에 `main`과 연결된 `docs/FULL_SCOPE_TRACEABILITY.md`, `docs/API_CONTRACT.md`, `database/FULL_DATABASE_MODEL.md` 중 관련 문서를 읽고 미확정 요구사항을 기록합니다.
2. **CI→GHCR→Ubuntu Pull 자동배포 정상, /api/version 기대 SHA, DB volume·Seed/권한, 프런트 페이지/API/헬스 확인; 성공/실패 구분.**
3. 기존 운영과 분리된 개인 브랜치(`task/t30-short-name`)에서 작업하고, 관련 코드·테스트·설명서를 함께 작성합니다.
4. 가능하면 로컬 또는 일회용 DB에서 먼저 검증하고, 승인 없이 공유 Staging DB·서비스를 변경하지 않습니다.

## 3. 산출물
docs/deployment/RELEASE_EVIDENCE.md; SHAs/digests/health; rollback runbook.

## 4. 완료 기준 (Definition of Done)
- 승인 릴리스의 화면/API/DB/버전과 상태 Healthy PASS, DB/복구 검증.
- 테스트·실행 결과와 재현 명령을 PR 설명에 기록합니다.
- 문서/코드/테스트의 PR 리뷰 완료 및 CI 결과를 확인합니다. CI가 범위를 검증하지 못하면 `PARTIAL`로 표기합니다.
- 작업과 무관한 파일 변경이 없고 민감정보·비밀번호·토큰이 포함되지 않습니다.

## 5. 필수 증빙
- 실제 실행 명령 또는 UI 캡처(비밀정보 마스킹)
- 정상 및 예외/거부 케이스 각각 1개 이상 (해당되는 경우)
- PR URL, 테스트 실행 SHA, 영향 범위와 미해결 항목

## 6. 주의·작업 중단 조건
대상 외 운영 Docker 프로젝트 금지, DB volume 보존, 자동 migration 금지.
