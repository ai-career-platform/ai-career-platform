## 4. 병목 분석

1. **처리량 포화는 동시성 4~8에서 옵니다. DB가 아니라 단일 Python 프로세스 때문입니다.**
   - 동시성을 더 올리면 처리량은 그대로이고 지연만 선형으로 늘어납니다(대기열).
   - CPU는 약 1.1~1.2 코어에서 멈추고 SQL p95는 수 ms로 낮습니다. 단일 uvicorn worker(+ 같은 프로세스 생성기)의 CPU가 한계입니다.
   - 확장 후보(승인 필요, 배포 설정): worker 수 증가 또는 인스턴스 추가. 이때는 `DB_POOL_SIZE × worker 수 ≤ DB max_connections` 계산이 필요합니다.
2. **DB 풀 5개가 동시성 8 이상에서 가득 찹니다(5/5).**
   - 32 과부하에서도 풀 대기 timeout(5초)·503·클라이언트 timeout은 **0건**이었습니다. 지연은 늘지만 오류로 바뀌지 않았습니다.
   - 실제 풀 timeout 경계는 이번 규모로 재현하지 않았습니다(NOT_RUN — 더 긴 SQL이나 큰 동시성 필요).
3. **`/me`는 요청당 SQL 5회입니다**(인증 4회: 세션·사용자·역할·권한 + 프로필).
   - 인증 의존성을 쓰는 모든 경로의 공통 비용입니다.
   - 캐시나 한 번의 조인 조회가 개선 후보지만 T15 보안 설계(매 요청 DB 재조회로 즉시 권한 회수)와 맞바꿈이 있어 **제안만** 합니다.
4. **AI 사용량 일별 집계가 가장 무거운 쿼리입니다**(2만 행에서 SQL 약 6 ms).
   - 행 수에 비례해 커집니다. 데이터가 커지면 일별 사전 집계 표 등이 후보입니다(Migration 필요 — 제안).
5. **공고 `ILIKE '%q%'`는 B-tree를 쓸 수 없습니다.**
   - 지금은 정렬 인덱스를 따라가며 걸러서 빠르지만, 드문 검색어나 큰 표에서는 전체 탐색에 가까워집니다.
   - 후보: `pg_trgm` GIN 인덱스(Migration·확장 승인 필요 — 제안).
