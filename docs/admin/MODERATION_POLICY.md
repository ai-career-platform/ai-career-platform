
# T80 — 운영 콘텐츠 검수 정책·상태 모델

> 상태: DRAFT / REVIEW_REQUIRED
> 기능 ID: F-027
> 관련 화면: UI-027
> 담당 영역: 기획/보안
> 선행 일감: T04, T05, T06
> 정책 승인: 미완료

## 1. 문서 목적

이 문서는 AI Career Platform에서 기업·채용 공고·사용자 콘텐츠의 검수 기준과 상태 전이, 승인 권한 및 이의제기 절차를 정의하기 위한 정책 초안이다.

본 문서의 내용은 제안 사항이며, PM 및 관련 담당자의 승인 전까지 확정된 운영 정책으로 취급하지 않는다.

실제 사용자 콘텐츠 삭제, 운영 데이터베이스 수정, Staging 및 운영 환경 변경은 별도 승인 전까지 금지한다.
  
  
## 2. 검수 대상 및 범위 (승인 전 초안)

본 정책의 검수 대상 후보는 다음과 같다.

| 대상 | 검수 기준 후보 | 확정 여부 |
|---|---|---|
| 기업 정보 | 허위 정보, 부정확한 기업 소개 | PM 검토 필요 |
| 채용 공고 | 허위 채용 조건, 부적절한 비용 요구 | PM 검토 필요 |
| 사용자 콘텐츠 | 스팸, 개인정보 노출, 부적절한 콘텐츠 | PM 검토 필요 |

### 미확정 사항

- 어떤 콘텐츠를 필수 검수 대상으로 지정할 것인가?
- 검수는 게시 전 또는 게시 후에 진행하는가?
- 자동 검수와 운영자 검수를 구분할 것인가?
- 검수 대상에서 제외할 콘텐츠가 있는가?

위 사항은 T04 요구사항 확정 및 PM 검토 후 결정한다.


## 3. 검수 상태 모델 (승인 전 초안)

### 3.1 상태 정의

| 상태 | 의미 |
|---|---|
| PENDING | 검수 요청이 접수되어 대기 중 |
| IN_REVIEW | 운영자가 검수를 진행 중 |
| APPROVED | 검수 승인 결정 |
| REJECTED | 검수 반려 결정 |
| APPEALED | 반려 결과에 대한 이의제기 접수 |

※ 위 상태 이름과 흐름은 설계 후보이며 PM 승인 전까지 확정하지 않는다.

### 3.2 상태 전이 후보

- PENDING → IN_REVIEW: 담당자가 검수를 시작한다.
- IN_REVIEW → APPROVED: 승인 권한자가 승인한다.
- IN_REVIEW → REJECTED: 승인 권한자가 반려한다.
- REJECTED → APPEALED: 신청자가 반려 결과에 이의제기한다.
- APPEALED → IN_REVIEW: 재검토가 시작된다.

### 3.3 예외 및 보안 검토

- 권한이 없는 사용자는 승인·반려할 수 없다.
- 동일한 검수 요청을 중복 처리하지 않도록 한다.
- 승인 또는 반려 시 사유 기록이 필요한지 검토한다.
- 이의제기 허용 횟수와 처리 기한은 PM 승인 후 확정한다.
- 모든 상태 변경은 감사 기록을 남기는 방향으로 검토한다.
- 이의제기 이후 최종 상태와 종료 조건은 추가 설계가 필요하다.

### 3.4 미확정 사항

- 승인·반려 권한을 가진 운영자 역할
- 검수 및 이의제기 처리 기한
- 반려 사유의 필수 여부와 분류 기준
- 재검토 이후 승인·반려 처리 방식
- 이미 승인된 콘텐츠를 재검수하는 조건
- 상태 변경 시 사용자 알림 여부


## 4. 검수 역할 및 권한 정책 (승인 전 초안)

### 4.1 역할별 권한 후보

| 역할 | 허용 작업 후보 | 제한 사항 |
|---|---|---|
| 기업 담당자 | 자신의 공고 검수 요청 및 이의제기 | 직접 승인·반려 불가 |
| 일반 사용자 | 권한이 있는 콘텐츠의 신고·이의제기 | 타인의 요청 정보 조회 불가 |
| 검수 운영자 | 검수 목록 조회, 승인·반려 검토 | 부여받은 권한 범위 내 처리 |
| 관리자 | 검수 정책 관리 및 이의제기 최종 검토 | 권한 및 감사 기준 준수 |

※ 실제 역할 이름, 승인 권한, 최종 결정권은 PM 및 보안 담당자 검토 후 확정한다.

### 4.2 권한 및 보안 원칙

1. 로그인하지 않은 사용자의 관리자 검수 기능 접근을 차단한다.
2. 승인·반려 요청은 서버에서 권한을 재검증한다.
3. 사용자는 권한이 없는 다른 사용자의 검수 요청을 조회하거나 변경할 수 없다.
4. 승인·반려·이의제기 처리 과정은 감사 기록을 남기는 방향으로 설계한다.
5. 동일한 요청의 중복 처리 및 상태 충돌을 방지한다.
6. 최소 권한 원칙을 적용한다.

### 4.3 미확정 사항

- 검수 운영자와 관리자의 역할 구분
- 최종 승인 및 반려 권한
- 본인이 등록한 콘텐츠를 직접 검수할 수 있는지 여부
- 이의제기 재검토 담당자 지정 방식
- 권한 변경 및 감사 기록 보존 기준


## 5. 반려 사유 및 이의제기 정책 (승인 전 초안)

### 5.1 반려 사유 분류 후보

| 코드 | 사유 | 예시 |
|---|---|---|
| FALSE_INFORMATION | 허위·부정확한 정보 | 사실과 다른 기업·채용 조건 |
| SUSPICIOUS_PAYMENT | 부적절한 비용 요구 | 채용 지원 과정에서 사전 입금 요구 |
| PERSONAL_DATA_EXPOSURE | 개인정보 노출 | 동의 없이 타인의 연락처 게시 |
| SPAM_CONTENT | 스팸·광고성 콘텐츠 | 반복 광고 및 무관한 게시물 |
| POLICY_VIOLATION | 기타 정책 위반 | 승인된 운영 정책 위반 |

※ 위 코드와 분류 기준은 제안 사항이며 PM 및 보안 담당자 승인 전까지 확정하지 않는다.

### 5.2 반려 처리 원칙 후보

1. 반려 시 사유 코드와 구체적인 설명을 기록한다.
2. 승인 권한이 없는 사용자는 반려 결정을 내릴 수 없다.
3. 반려된 콘텐츠를 자동 삭제하지 않는다.
4. 반려 결정 시각과 담당자를 감사 기록으로 남기는 방안을 검토한다.
5. 사용자에게 공개할 반려 사유와 내부 관리용 기록을 구분한다.

### 5.3 이의제기 처리 기준 후보

1. 이의제기는 해당 콘텐츠에 대한 권한이 있는 신청자만 제출할 수 있다.
2. 신청자는 반려 사유에 대한 설명이나 증빙을 제출할 수 있다.
3. 이의제기 요청 시 기존 반려 기록을 보존한다.
4. 재검토 담당자의 권한을 확인한다.
5. 재검토 결과와 사유를 기록한다.
6. 이의제기 가능 횟수와 제출 기한은 PM 승인 후 확정한다.
7. 이의제기 중 콘텐츠의 공개 여부는 정책 확정 전까지 미정으로 둔다.

### 5.4 미확정 사항

- 반려 사유 코드의 최종 목록
- 사유 코드별 증빙 요구 여부
- 이의제기 접수 및 처리 기한
- 이의제기 횟수 제한
- 재검토 담당자와 최종 결정권자
- 재검토 후 상태 전이 및 종료 조건
- 사용자에게 전달할 결과 안내 방식


## 6. 검수 처리 기한 및 우선순위 (승인 전 초안)

### 6.1 처리 기한 정책 후보

| 항목 | 처리 기한 | 확정 여부 |
|---|---|---|
| 일반 검수 요청 | PM 결정 필요 | 미확정 |
| 긴급 검수 요청 | PM 결정 필요 | 미확정 |
| 반려 결과 통지 | PM 결정 필요 | 미확정 |
| 이의제기 접수 | PM 결정 필요 | 미확정 |
| 이의제기 재검토 | PM 결정 필요 | 미확정 |

※ 법적 처리 의무나 서비스 운영 기한을 임의로 확정하지 않는다.

### 6.2 우선순위 기준 후보

- 일반: 통상적인 기업 및 채용 공고 검수
- 긴급: 개인정보 노출이나 이용자 피해 가능성이 있는 콘텐츠
- 보류: 검수에 필요한 정보나 증빙이 부족한 콘텐츠

위 분류는 운영 정책 후보이며 우선순위별 처리 시간은 미확정이다.

### 6.3 처리 지연 시 대응 후보

1. 요청 접수 시각을 기록한다.
2. 처리 기한이 승인된 경우 지연 여부를 확인한다.
3. 지연 건은 권한이 있는 담당자에게 전달한다.
4. 지연으로 인한 상태 변경은 자동으로 수행하지 않는다.
5. 담당자 지정 및 알림 방식은 추후 확정한다.


## 7. 예외 상황 및 보안 정책 (승인 전 초안)

### 7.1 예외 상황

| 상황 | 기대 처리 후보 |
|---|---|
| 미로그인 사용자 접근 | 인증 거부 (401 후보) |
| 권한 없는 승인·반려 요청 | 403 Forbidden |
| 존재하지 않는 검수 ID | 404 Not Found 후보 |
| 이미 처리한 요청에 중복 결정 | 409 Conflict 후보 |
| 잘못된 상태 전이 | 409 Conflict 후보 |
| 필수 입력값 누락 | 입력 검증 오류 (400/422 등 계약 확인 필요) |
| DB 또는 서버 오류 | 오류 기록 및 안전한 실패 처리 |

※ 실제 HTTP 상태 코드는 API_CONTRACT.md와 T06 승인 결과를 따른다.

### 7.2 보안 원칙

1. 관리자 권한은 서버에서 검증한다.
2. 검수 대상에 대한 접근 권한을 확인한다.
3. 비밀정보와 개인정보는 로그에 직접 기록하지 않는다.
4. 상태 변경 시 요청자, 권한, 대상 및 현재 상태를 검증한다.
5. 중복 요청과 동시성 충돌을 방지하는 방안을 검토한다.
6. 승인 전 실제 사용자 콘텐츠를 삭제하지 않는다.
7. 운영 및 공용 Staging 설정을 임의로 변경하지 않는다.

### 8.1 검수 데이터 모델 후보

|---|---|---|

| status | 현재 검수 상태 | 미확정 |
| requester_id | 요청자 식별자 | 미확정 |

| reviewed_at | 검수 결정 시각 | 미확정 |

### 8.2 감사 이벤트 후보

- REVIEW_REQUESTED: 검수 요청 접수
- REVIEW_STARTED: 검수 시작
- REVIEW_APPROVED: 검수 승인
- REVIEW_REJECTED: 검수 반려
- APPEAL_SUBMITTED: 이의제기 접수
- APPEAL_REVIEW_STARTED: 이의제기 재검토 시작
- REVIEW_DECISION_CONFLICT: 중복 결정 또는 상태 충돌

※ 이벤트 이름과 저장 방식은 승인 전 제안 사항이다.

### 8.3 데이터 설계 관련 미해결 사항

- moderation_reviews 테이블의 실제 생성 여부
- 검수 이력과 이의제기 이력의 분리 여부
- 검수 대상 종류별 참조 관계
- 상태 변경 이력의 보존 방식
- 감사 로그 접근 권한 및 보존기간
- 기존 DB 테이블과의 호환성

위 사항은 T05 DB 설계 담당자와 협의하여 결정한다.


## 9. 검증 및 테스트 계획 (승인 전 초안)

### 9.1 정상 흐름

- 검수 요청이 정상적으로 접수된다.
- 권한이 있는 운영자가 검수를 시작한다.
- 승인 또는 반려 시 상태가 변경된다.
- 반려된 콘텐츠에 대해 이의제기 요청이 가능하다.
- 재검토 결과와 이력이 보존된다.

### 9.2 오류 및 보안 검증

- 미로그인 사용자의 관리자 기능 접근 거부
- 권한 없는 사용자의 승인·반려 요청 거부
- 존재하지 않는 검수 대상 처리
- 중복 승인 또는 반려 요청 차단
- 허용되지 않은 상태 전이 차단
- 입력값 누락 및 잘못된 사유 코드 검증
- 개인정보와 비밀정보의 로그 노출 방지

### 9.3 테스트 환경

- 정책 검토 및 문서 기반 테스트를 우선한다.
- 필요한 경우 Mock 데이터를 사용한다.
- 실제 사용자 개인정보를 테스트 데이터로 사용하지 않는다.
- 공유 Staging DB와 운영 환경은 승인 없이 변경하지 않는다.
- Mock 테스트만 통과한 경우 실제 연동 완료로 보고하지 않는다.


## 10. 승인 필요 사항 및 작업 제한

### 10.1 PM 및 관련 담당자 승인 필요

- 최종 검수 대상과 검수 기준
- 승인 및 반려 권한
- 검수 처리 기한
- 이의제기 처리 및 종료 조건
- 상태 코드와 상태 전이 규칙
- 반려 사유 코드
- 데이터 테이블 및 컬럼 설계
- 감사 기록 및 보존 정책
- 실제 API 연동 범위

### 10.2 선행 작업 확인

| 작업 | 확인된 상태 | 완료 증빙 |
|---|---|---|
| T04 | READY_FOR_REVIEW | 미확인 |
| T05 | READY_FOR_REVIEW | 미확인 |
| T06 | 확인 필요 | 미확인 |

※ READY_FOR_REVIEW는 완료 또는 승인 상태를 의미하지 않는다.

### 10.3 구현 제한

T04, T05, T06의 완료 결과 또는 명시적 Mock 계약이
확인되지 않은 상태에서는 실제 API 및 DB 연동을 진행하지 않는다.

정책 승인 전 사용자 콘텐츠 자동 삭제, 공용 Staging DB 변경,
