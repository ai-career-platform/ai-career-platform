# Staging PostgreSQL · Schema · Seed 운영 정책

## 원칙
- Staging DB는 **공동 통합 테스트용**입니다. 실제 개인정보/운영 비밀정보를 넣지 않습니다.
- 개발자는 원칙적으로 **읽기 전용**으로 직접 접속; 변경은 Backend API를 통한 테스트 또는 승인된 Migration으로 처리합니다.
- **공통 Seed 데이터는 개발 시작 전에 배포**하고, 자동 배포로 초기화하거나 매번 롤백하지 않습니다.
- DB Schema 변경은 개발자가 요청하고 **PM/JM 검토 후 반영**합니다.
- 자동 배포는 DB Migration을 자동 실행하지 않는 것이 초기 정책입니다.

## 역할/계정 설계안 (아직 생성·배포 여부 별도 검증)
| 역할 | 예시 계정 | 허용 범위 |
|---|---|---|
| 개발자 조회 | `career_reader` | 필요 스키마 SELECT; DDL/DML 불가 |
| Backend 앱 | `career_app` | 필요 테이블에 제한된 CRUD, DDL 금지 |
| Migration 수행 | `career_migrator` | 승인된 DDL·Migration 실행 |
| PM/JM 운영 관리자 | 별도 관리자 역할 | 권한/스키마 관리, 감사 |
| PostgreSQL SUPERUSER | 비상용 | 일상 사용 금지 |

- 초기에는 공용 reader 계정을 고려할 수 있지만, **누가 조회했는지 감사 추적이 필요한 경우 개인 계정**을 권장합니다.
- `career_app` 비밀번호는 Vault/Secret Manager 통합을 목표로 합니다. 도입 전까지는 소유자만 읽는 `.env`를 임시 사용하되 Git에 포함하지 않습니다.
- PostgreSQL 5432를 인터넷에 직접 공개하지 않습니다. 승인된 VPN/SSH 터널로 접근합니다.
- 조회 제한시간, 연결 수, 민감 데이터 마스킹을 적용합니다.
- 기존 호스트에 별도로 존재하는 PostgreSQL 및 ngrok TCP 터널은 이 PoC DB와 별개이며 보안 점검 대상입니다.

## DB 변경 절차
개발자 Redmine DB 요청 → ERD/DDL·영향 범위·Migration·복구안 첨부 → PM/JM 리뷰 → 승인 PR Merge → 백업/복구 가능성 확인 → PM/JM 실행 → API/Seed 검증 → 이력 기록.
- 파괴적 SQL, 데이터 대량 수정, 권한 변경은 사전 검토 없이 수행하지 않습니다.
- 변경 요청에 기존 API 호환성과 테스트/롤백 또는 복구 절차를 명시합니다.

## 초기 Schema/Seed
- 전체 화면에 필요한 테이블을 한 번에 확정하지 않습니다. 사용자, 프로필, 직무, 기술, 기업, 채용공고, 연결 테이블 등 공통 핵심부터 구축합니다.
- 초기 20~25개, 전체 45~65개 테이블은 **기획 단계 추정**이지 확정 설계가 아닙니다.
- Seed 예시 규모: 가상 사용자 20명, 기업 20개, 직무 30개, 기술 100개, 공고 100개. 실제 요구사항과 ERD에 맞춰 조정.
- Seed는 Idempotent하게 작성하여 재실행 시 중복을 막고, 데이터 출처·버전을 기록합니다.

## 테스트 데이터 보존
- 일반 개발·API 테스트용 가상 데이터는 원칙적으로 유지하고, 불필요한 중복·오염이 발생한 경우 승인된 정리 절차 사용.
- CI 자동화 테스트는 독립 테스트 DB/트랜잭션을 사용하여 공용 Staging을 오염시키지 않습니다.
- Docker Named Volume 보존; `docker compose down -v` 금지.
