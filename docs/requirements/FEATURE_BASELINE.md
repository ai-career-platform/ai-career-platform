## 4. 기능별 명세

각 기능 블록의 형식: **스토리**(사용자 관점) · **입력 → 출력** · **권한** · **화면 상태**(정상 외에 로딩/빈 상태/오류/권한 없음 중 해당) · **수용 기준** · **비기능 제약** · **근거** · **미결정**

공통 화면 상태(모든 화면에 적용, §5 N-11): 로딩 스켈레톤 · 네트워크 오류 + 재시도 · 401은 로그인으로 이동 후 원래 화면 복귀 · 403은 공통 접근 제한 안내 · 404는 공통 없음 화면.

### A. 계정·인증·프로필

**F-001 회원 가입/인증** — KEEP · Must
- 스토리: 구직자로서 계정을 만들고 로그인해서 내 프로필과 추천을 이어서 볼 수 있다.
- 입력 → 출력: 가입 수단(이메일 또는 외부 계정, D-01) → 로그인 세션
- 권한: `G` → 로그인 후 `U`
- 화면 상태: 잘못된 자격 증명 · 중복 가입(409) · 시도 횟수 초과(429) · 외부 로그인 취소
- 수용 기준: ① 가입 후 바로 로그인 상태가 된다 ② 같은 식별자로 두 번 가입할 수 없다 ③ 실패 메시지가 계정 존재 여부를 노출하지 않는다 ④ 가입 시 필수 동의(F-005)를 받는다
- 비기능: 비밀번호·토큰을 로그·응답에 남기지 않음(E8). 자체 인증이면 비밀번호 해시와 시도 제한 필수
- 근거: E4, E5 §2-A · 미결정: **D-01 인증 방식**, 이메일 인증 여부(N-03)

**F-002 로그아웃·세션** — KEEP · Must
- 스토리: 공용 PC에서 로그아웃하면 다른 사람이 내 정보를 볼 수 없다.
- 입력 → 출력: 현재 세션 → 세션 무효화
- 권한: `U`
- 화면 상태: 세션 만료 시 로그인 화면으로 이동 후 원래 화면 복귀
- 수용 기준: ① 로그아웃 후 이전 토큰으로 보호 API를 호출하면 401 ② 만료된 세션에서 작업 중이던 입력은 가능하면 보존
- 비기능: 세션 만료 시간 정의 필요 · 근거: E4, E6 A04 · 미결정: 세션 유지 기간, 다중 기기 동시 로그인 허용 여부

**F-003 계정·프로필** — KEEP · Must
- 스토리: 내 이름·한 줄 소개·지역을 적어 두면 추천과 매칭에 반영된다.
- 입력 → 출력: 표시 이름(1~100자), 한 줄 소개, 자기소개, 지역 → 저장된 프로필
- 권한: `U`·`O` (본인만 조회·수정)
- 화면 상태: 빈 상태(가입 직후 "프로필을 채우면 추천이 정확해집니다") · 입력 검증 오류(422)
- 수용 기준: ① 다른 사용자의 프로필은 ID를 바꿔 요청해도 볼 수 없다 ② 비운 필드와 수정하지 않은 필드를 구분해 저장한다
- 비기능: 개인정보 최소 수집 · 근거: E4, E5 `PATCH /me` · 미결정: 프로필 공개 범위(1차는 비공개 고정 제안, 공개는 T128)

**F-004 역할·접근권한** — **CHANGE** · Must
- 변경 내용: UI-004 "접근 제한 안내"는 독립 화면이 아니라 **모든 화면 공통의 403 상태**(N-11)로 바꿉니다. 기능 자체(역할 조회, 관리자 경로 차단)는 유지합니다.
- 스토리: 운영 관리자가 아니면 관리자 메뉴가 보이지 않고, 주소를 직접 입력해도 들어갈 수 없다.
- 입력 → 출력: 로그인 세션 → 내 역할·권한 목록
- 권한: `U`
- 수용 기준: ① `/admin` 화면·API는 `M`만 접근 ② 화면에서 메뉴를 숨기는 것과 별개로 서버에서 다시 검사 ③ 역할 회수 즉시 반영(E8)
- 근거: E4, E5, E8 · 미결정: 관리자 권한 부여 절차(누가 누구에게)

**F-005 동의·탈퇴·보존** — **CHANGE** · Must
- 변경 내용: 하나로 묶인 기능을 **(a) 동의 관리**와 **(b) 탈퇴 요청**으로 나누고, (b)에 필요한 **탈퇴 요청 데이터**를 T05에 추가 요청합니다(E5 §4에서 누락 확인).
- 스토리: (a) 내가 어떤 약관·처리방침에 동의했는지 보고 선택 동의는 철회할 수 있다. (b) 탈퇴를 요청하면 언제 무엇이 지워지는지 안내받는다.
- 입력 → 출력: (a) 정책 코드·버전·동의 여부 → 동의 이력 (b) 확인 입력 → 요청 ID·처리 상태
- 권한: `U`·`O`

- 스토리: 관심 직무의 공고 수·요구 기술 추세를 기간별로 본다.
- 입력 → 출력: 직무, 지표, 기간 → 관측값 + 예측값 + 출처
- 권한: `U` (G 공개 여부 D-03)
- 화면 상태: 데이터 부족 기간 · 예측 불확실성 범위 표시
- 수용 기준: ① 관측값과 예측값을 시각적으로 구분 ② 출처·집계 기간 표시
- 근거: E2 · 미결정: **D-05 데이터 출처·라이선스**(T61)

**F-025 군집·행동·이상탐지** — **CHANGE** · Could
- 변경 내용: E5에서 권한이 "A, 권한 범위"로 모호합니다. **운영 관리자 전용**(`M`, `/admin`)으로 바꿉니다. 일반 사용자에게 세그먼트·이상탐지를 보여줄 근거가 없습니다.
- 수용 기준: ① 개인 식별 없는 집계만 표시 ② 행동 데이터는 동의한 사용자만 수집(F-005)
- 근거: E2, E5 · 미결정: 행동 이벤트 수집 동의(T71)

**F-026 모델 버전·품질** — KEEP · Should
- 스토리: 운영 관리자가 지금 서비스 중인 규칙·모델 버전과 평가 지표를 본다.
- 입력 → 출력: 페이지 → 모델 버전 목록, 버전별 평가 지표
- 권한: `M` · 수용 기준: ① 사용자 결과(F-015~017)에 표시되는 버전과 같은 ID 체계
- 근거: E2 · 미결정: 없음(형식은 T25·T60)

**F-027 운영 콘텐츠 검수** — **DROP** (1차 기준선)
- 이유: 1차 범위에는 사용자가 공개 게시하는 콘텐츠가 없습니다(공고는 Seed/수집, 프로필은 비공개, 기업 게시는 T121 이후). 검수 대상이 없는 상태에서 화면·API를 만들면 빈 기능이 됩니다. E5 §4에서 데이터 모델도 없음이 확인됐습니다.
- 이관: T80~T82(검수 정책·큐·UI), T125(기업 공고 검수). 기업 사용자(D-02)나 공개 포트폴리오(T128)를 1차에 넣기로 하면 다시 KEEP으로 바꿉니다.

**F-028 감사·AI 비용 기록** — KEEP · Should
- 스토리: 운영 관리자가 권한 변경·삭제 같은 중요한 행위와 AI 호출 비용을 기간별로 본다.
- 입력 → 출력: 기간, 행위자, 행위 종류 / 기간, 모델 → 감사 이벤트 / 사용량 합계
- 권한: `M`
- 수용 기준: ① 감사 기록은 수정·삭제 불가 ② 원문 프롬프트·개인정보는 기록하지 않음
- 근거: E2, E8 · 미결정: 보존 기간(D-06)

**F-029 기준 데이터 Seed·버전** — KEEP · Must (비기능, 화면 없음)

**F-030 Staging 건강상태** — KEEP · Must (비기능, 화면 없음)

- 근거: E11 (구현 사실)
