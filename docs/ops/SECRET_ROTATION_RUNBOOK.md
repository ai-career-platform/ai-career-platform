# Secret 회전·유출 대응 Runbook (T111)

> 상태: **PROPOSED**, PM 승인 전입니다.
> - 이번 일감에서는 **실제 Secret을 회전하지 않았습니다.**
> - 절차는 합성 키 A→B→A 시뮬레이션(`backend/tests/test_t111_env_contract.py`)으로만 검증했습니다.
> - 실행 권한: PM 승인 후 Staging 서버 관리자. 개발자에게 실제 값을 전달하지 않습니다(T111 §5).

## 1. 대상과 영향

| Secret | 쓰는 곳 | 회전하면 생기는 일 (시뮬레이션 결과) |
|---|---|---|
| `JWT_SECRET` | access token 서명(HS256), 목록 cursor 서명(`derive_key`) | ① 기존 access token 즉시 401(fail-closed) ② **refresh token은 유지**됨. 서버에 SHA-256 해시로만 저장되고 키와 무관하므로 클라이언트가 `/auth/refresh`로 새 키 토큰을 받아 재로그인 없이 복구됨 ③ 진행 중인 목록 cursor는 서명이 바뀌어 거부됨(첫 페이지부터 다시 조회) |
| `DATABASE_URL` 비밀번호(`career_app`) | Backend DB 연결 | 새 비밀번호를 DB에 먼저 추가할 수 없다(PostgreSQL 역할당 비밀번호 1개). 겹치는 시간 없이 교체하려면 **두 번째 앱 역할**을 쓰는 방식(§3-2)이 필요 |
| `POSTGRES_PASSWORD`(관리자) | Compose DB 컨테이너 초기화·관리 | 앱은 쓰지 않음. 관리자만 교체 |
| `CRAWLER_STAGING_DATABASE_URL` | 수집기 | 수집기 정지 시간에 교체 |

## 2. 정기 회전 — JWT_SECRET (중단 최소화)

| 단계 | 할 일 | 확인 | 실패 시 |
|---|---|---|---|
| 0 | PM 승인, 시간대 공지(로그인 화면 영향 없음, 진행 중 페이지 이동만 처음부터) | 승인 기록 | 중단 |
| 1 | 새 키 B 생성: `python -c "import secrets;print(secrets.token_urlsafe(48))"`. 서버에서만 실행하고 터미널 기록·채팅에 남기지 않음 | 길이 ≥ 32 | — |
| 2 | 서버 비공개 `.env`의 `JWT_SECRET`을 B로 교체. 기존 값 A는 서버 안 별도 파일(0600)에 **복귀용으로만** 24시간 보관 | `python -m app.core.env_contract --target staging` exit 0 | 값 되돌림 |
| 3 | Backend 컨테이너 재생성(기존 Auto-CD 절차 그대로, 정책 변경 없음) | `/health` 200, `/version` SHA 동일 | 기동 실패면 이전 컨테이너 유지(새 키가 32자 미만이면 기동 단계에서 거부됨, 시험으로 확인) |
| 4 | 스모크: 로그인 → 보호 API 200, 기존 브라우저 탭은 401 후 자동 refresh로 복구 | 401 비율이 수 분 안에 정상화 | §2-복귀 |
| 5 | 24시간 뒤 A 보관 파일 삭제, 회전 기록(날짜·담당·사유, 값 없음) | 기록 | — |

**복귀(B→A)**: `.env`를 A로 되돌리고 재생성합니다. B로 발급된 access token은 401이 되지만 refresh로 복구됩니다. 시뮬레이션 3단계에서 확인했습니다.

### 2-1. 무중단 이중 키 (PROPOSED, 미구현)

- 현재 코드는 키 하나만 검증합니다. 그래서 회전 직후 짧은 401 구간이 생깁니다(access TTL 최대 15분, refresh로 바로 복구).
- 401조차 없애려면 `JWT_SECRET_PREVIOUS`(검증만 하고 서명은 안 함)를 추가하는 방안이 있습니다.
- 이는 인증 코드 변경이라 **이번 PR에 넣지 않았습니다.** 보안 리뷰와 PM 승인이 필요합니다.
- 넣을 경우의 조건:
  - 이전 키 유효기간은 access TTL 이하로 제한
  - cursor 서명에는 적용하지 않음
  - 시험으로 이전 키 토큰의 만료를 확인

## 3. 정기 회전 — DB 앱 계정 비밀번호

1. **단일 역할(현재)**:
   - `ALTER ROLE career_app PASSWORD …`과 `.env` 교체 사이에 연결이 실패하는 구간이 생깁니다.
   - 기존 연결은 유지되지만, 새 연결(풀 확장·재시작)은 실패합니다.
   - 트래픽이 적은 시간에 진행하고, 바로 컨테이너를 재생성합니다.
2. **두 역할 교대(PROPOSED)**:
   - `career_app_a`와 `career_app_b`가 같은 그룹 역할(`career_app`)을 상속하게 합니다.
   - 쉬는 쪽 비밀번호를 바꾸고 `.env`를 그 역할로 바꾼 뒤 재생성합니다. 나머지 쪽은 다음 회전 때 바꿉니다.
   - DB 역할을 추가해야 하므로 **공유 DB 변경 승인 전에는 HOLD**입니다.

## 4. 유출 대응 (의심 포함)

| 순서 | 할 일 | 기준 |
|---|---|---|
| 1 | 범위 판단: 어떤 Secret이, 어디에(GitHub·로그·채팅·스크린샷), 언제부터 | 15분 안 |
| 2 | **즉시 회전**(§2·§3, 승인은 사후 기록 가능한 긴급 절차: PM에게 바로 연락) | `JWT_SECRET`이 유출되면 토큰 위조가 가능하므로 최우선 |
| 3 | 세션 무효화: `JWT_SECRET` 유출 시 refresh 세션까지 끊어야 함. 위조된 access token으로 refresh를 받을 수는 없지만 위조 토큰 자체가 TTL 동안 유효했으므로, 감사 로그로 그 기간 활동을 확인 | 감사 로그 확인 |
| 4 | GitHub 노출: 커밋 되돌리기로는 부족(이력에 남음). **회전이 우선**이고 이력 정리는 PM 결정(강제 push 금지 정책과 충돌) | 회전 완료 확인 |
| 5 | 재발 방지: 스캔 규칙 추가, 사후 보고 | 사후 보고서 |

## 5. 막는 장치 (이번 PR에서 시험으로 확인)

- `.env`, `.env.*`는 Git 제외 대상입니다(`!.env.example`만 허용). 추적 중인 실제 `.env`나 키 파일(`*.pem`, `id_rsa` 등)이 0건임을 확인합니다.
- 예제 파일(`*.env.example`, `.env.mock`)의 Secret 이름 변수는 빈 값이나 자리표시자만 허용합니다.
- 설정 객체 `repr`, 설정 오류 메시지, 기동 로그, `/version` 응답에 Secret이 나오지 않습니다(표식 문자열로 확인).
- 계약 검사 CLI는 이름과 문제 종류만 출력합니다.
