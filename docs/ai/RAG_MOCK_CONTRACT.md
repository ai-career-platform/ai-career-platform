# T25 → T53/T54 RAG 가상 연동 계약 제안

**상태: 설계 기준선 수용 / 실제 구현 HOLD / 합성 데이터 전용.** T53·T54 담당자가 로컬 Mock을 논의할 때 사용할 예시다. 팀의 동의나 실제 시스템의 권한·삭제·DB/API 계약을 대체하지 않는다. T25 실연동 완료가 아니며 T49 문서 저장, T15 인증 및 담당자 간 세부 구현 협의가 필요하다.

근거: [T53 작업지시서](../work-orders/next-30/T53.md), [T54 작업지시서](../work-orders/next-30/T54.md), [AI 구조](../AI_SYSTEM_ARCHITECTURE.md), [T25 초안](FEATURE_CONTRACT.md). T53·T54 지시서는 선행 결과 **또는 명시적인 Mock 계약**이 있으면 Mock 작업을 할 수 있다고 설명하지만, 아래 내용의 채택 여부는 담당자 간 확인해야 한다.

## 1. 가상 문서와 청크

```json
{
  "document_id": "demo-document-01",
  "owner_id": "demo-user-a",
  "visibility": "private",
  "document_version": "demo-v1",
  "access_version": "demo-acl-v1",
  "index_version": "demo-index-v1",
  "deleted": false,
  "chunks": [
    {"chunk_id": "demo-chunk-01", "position": 0, "content": "가상 문서 내용"}
  ]
}
```

모든 값은 가상 예다. `document_id`/`chunk_id`는 문서·조각을 구분하고, `owner_id`/`visibility`는 가상 접근 검사, 세 가지 버전은 원본·접근 조건·색인의 동기화 상태를 검토하기 위한 후보 이름이다. 실제 저장 구조·ID 형식·공개 범위·해시·청크 크기 및 라이선스는 미확정이다. 실제 문서나 개인정보를 fixture·로그에 넣지 않는다.

## 2. 제안하는 Mock 동작과 검증 사례

| 상황 | Mock에서 검토할 기대 동작 | 최종 결정 필요 |
|---|---|---|
| 사용자 A가 A의 유효 문서를 검색 | 해당 문서 청크만 결과 후보로 제공 | 인증 주체와 공개 범위 |
| 사용자 B가 A의 비공개 문서를 검색 | 청크·문서 내용이 결과에 나오지 않음 | 오류 코드와 존재 여부 노출 정책 |
| 접근 권한이 변경됨 | 이전 권한으로 반환하지 않고 색인 상태를 갱신하거나 안전하게 제외 | 전파 시점·지연·실패 처리 |
| 문서 삭제 또는 동의 철회 | 해당 청크를 검색 결과에서 제외하고 색인 정리 확인 | 삭제·보존·동의 철회 범위 및 책임 |
| 결과 없음 또는 색인 장애 | 각각 빈 결과 또는 오류로 구분, 원문·비밀을 로그에 남기지 않음 | HTTP 형식·오류 코드·대체 동작 |

검색 인덱스의 필터만으로 최종 API 인가가 완성됐다고 간주하지 않는다. Mock의 `owner_id`는 인증된 사용자라는 증거가 아니며, 사용자·기업·공개 문서의 실제 접근 규칙은 T15/T49/T53/T54 및 PM이 정한다. PM은 조회 전과 반환 전 검증 및 fail-closed 원칙을 결정했다. 오래된 색인 정보와 장애 시 이를 구현·검증하는 방법은 협의해야 한다.

## 3. T53·T54 담당자와 확인할 질문

1. 문서 종류와 접근 범위(개인·공용·기업)를 어디에서 확정하고, 요청자의 신원을 어떤 인증 계약으로 받는가?
2. 청크 식별자/위치/해시와 인덱스 버전은 어떤 형식이며 중복 및 빈 문서를 어떻게 다룰 것인가?
3. 원본 삭제·권한 변경·동의 철회의 대상과 전파 시점, 실패 시 재시도·일시적 검색 차단 기준은?
4. T49 문서 상태와 T06 검색 DTO·오류 계약이 미완성일 때, 위 Mock 필드와 검증 사례를 임시 인터페이스로 사용해도 되는가?
5. 벡터 저장소·임베딩 모델이 승인되기 전 어떤 Mock 어댑터와 테스트 경계까지 허용되는가?

## 4. 한계

이 문서는 논의를 위한 텍스트 예제다. 위 JSON은 검증된 스키마가 아니고, 권한 동기화·삭제 전파·API·DB·색인 구현이나 실제 데이터 보안 테스트를 수행하지 않았다. PR #26 설계 기준선은 병합됐고 합성 CI가 통과했다. 실제 시스템에 대한 검증은 별도다.

## 5. T06 병합본과 공개 경계 확인 (2026-11-06)

T06 OpenAPI의 `askKnowledge` 설명은 검색 API를 공개하지 않고 Q&A 엔드포인트 내부에서 사용한다고 명시한다. PM은 T53/T54를 내부 검색 인터페이스로 사용하고 1차에서 별도 외부 검색 API를 만들지 않기로 결정했다. T06의 KnowledgeAnswer는 status(`answered`/`no_evidence`), answer, citations, limitations 등을 요구한다. 이 문서의 가상 청크는 내부 Mock 후보이며 공개 API 계약 확정이나 권한 구현을 뜻하지 않는다.

## 6. PM 결정과 남은 구현 (2026-11-09)

[PR #26 PM 결정](https://github.com/ai-career-platform/ai-career-platform/pull/26#issuecomment-6730998767)에 따라 기존 T15 인증을 재사용하고 검색 전 및 반환 직전 권한을 확인한다. 권한 미확인·해제·삭제·동의 철회 대상은 결과에서 제외한다. 색인 정리 지연 중에도 접근 차단이 우선이다. 색인 정리 이벤트·지연·재시도와 검증의 구체적인 계약 및 실제 구현은 T53/T54와 Backend 담당 협의 전 HOLD다. 위 합성 예제의 owner_id는 인증이나 인가를 수행하지 않는다.
